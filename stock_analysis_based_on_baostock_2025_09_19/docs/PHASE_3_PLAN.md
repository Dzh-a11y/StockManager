# StockManager 第三阶段计划：本地 Web 可视化与规则自动扩展

StockManager 是 A 股研究型筛选平台，禁止自动交易；所有筛选结果仅供研究参考，不构成任何投资建议。

## 阶段目标

P3 在 P2 参数化规则后端之上增加一个本地、离线优先的 Web 操作界面。用户可以在 HTML 页面中选择模板、开关规则、修改参数、调整 `all`/`any` 组合、保存用户模板并运行筛选。

P3 的关键架构目标不是“为现有八条规则手写八份表单”，而是建立一条元数据驱动链路：后端新增并注册可信规则后，API 从 `RuleDefinition` 输出规则目录，前端根据参数定义自动生成控件。普通新规则不得要求修改筛选主循环、HTTP 路由或前端规则清单。

## 范围

- 本机 HTTP 服务与纯 HTML、CSS、JavaScript 页面。
- 动态规则目录、模板 CRUD、模板校验和离线筛选 API。
- 参数控件、规则开关、分组组合与模板版本可视化。
- 筛选结果总览、股票结果表和逐规则执行详情。
- “新增普通规则，前端自动出现”的契约测试。
- 全部接口和筛选测试断网可运行。
- 技术文档、使用说明与 Obsidian 同步。

## 排除范围

- 自动交易、下单、回测、实时行情和投资建议。
- 浏览器直接访问 Baostock 或任何 Provider。
- 筛选时自动同步或补拉缺失数据。
- 用户登录、远程部署、多租户和云端模板共享。
- React、Vue、Node 构建链或外部 CDN；除非用户另行批准技术选型。
- 运行时上传 Python 文件、模板指定导入路径或执行第三方规则代码。
- 在浏览器请求中提交数据库路径、模板根目录或 Provider 凭据。

## 强制架构边界

```text
HTML / CSS / JavaScript
  -> Local HTTP API
  -> TemplateService / TemplateCompiler
  -> ParameterizedScreeningService
  -> LocalRepositoryProtocol
  -> SQLite

BaostockProvider
  -> DataSyncService
  -> SQLite
```

- HTTP API 和页面只允许通过 P2 服务层读取本地数据。
- Web 启动时由受控配置提供 SQLite 和模板目录；浏览器不能决定文件路径。
- API 层只负责解析、校验、状态码和 JSON 格式，不实现筛选公式。
- Rules 与 Domain 不依赖 HTTP、HTML、JavaScript、数据库或 Provider。
- 页面规则表单必须来自规则目录 API，禁止维护硬编码 `rule_id` 列表。
- 模板必须继续经过 `parse_template` 和 `TemplateCompiler`；前端校验不能替代后端校验。
- 系统模板只读，用户模板使用 revision 乐观并发控制。

## 拟定接口

最终字段以 P3-0 的 ADR 和契约测试为准。

### 页面与静态资源

- `GET /`：筛选工作台。
- `GET /styles.css`：本地样式。
- `GET /app.js`：本地交互逻辑。

### 规则目录

- `GET /api/rules`
- 返回所有已注册 `RuleDefinition`。
- 每条规则至少包含 `rule_id`、名称、说明和参数定义。
- 参数定义至少包含类型、必填、默认值、最小值、最大值、标签和说明。

### 模板

- `GET /api/templates`：模板摘要列表及系统/用户属性。
- `GET /api/templates/{template_id}`：完整模板。
- `POST /api/templates/validate`：解析并编译临时模板，不保存。
- `POST /api/templates`：创建 revision 1 用户模板。
- `PUT /api/templates/{template_id}`：携带 `expected_revision` 更新。
- `DELETE /api/templates/{template_id}`：携带 `expected_revision` 删除用户模板。

### 筛选

- `POST /api/screen`
- 请求包含临时完整模板、`dataset_id`、交易日、显式复权和可选股票代码列表。
- 响应包含股票代码、名称、总体通过状态、模板 ID/revision、数据集元数据和逐规则 `PASSED`/`FAILED`/`SKIPPED` 详情。
- 本地数据不足时返回明确业务错误，不调用同步服务。

### 错误映射

- `400`：请求结构、模板、参数、日期或复权错误。
- `403`：尝试修改系统模板。
- `404`：模板、静态资源或本地数据不存在。
- `409`：模板重复或 revision 冲突。
- `500`：未预期服务器错误；记录诊断信息但响应不得泄露本机路径或堆栈。

## 页面信息架构

页面按三栏或等价响应式布局组织：

1. **运行条件**：数据集、交易日、复权、可选股票代码。
2. **策略编辑器**：模板元数据、规则卡片、参数控件、规则开关、分组和 `all`/`any`。
3. **筛选结果**：总数、通过数、失败数、结果表和逐规则详情。

交互要求：

- 首次加载读取规则目录与系统默认模板。
- 参数类型自动映射为数字、文本或布尔控件。
- 禁用规则不进入有效组合，并在结果中显示为 `SKIPPED`。
- 修改后明确显示“未保存”，筛选临时配置不得自动覆盖模板。
- 创建、更新、另存为和删除有清晰区别。
- revision 冲突提示用户重新加载，不静默覆盖。
- 请求执行期间防止重复提交，并显示运行、成功或失败状态。
- 页面必须显示“仅供研究参考，不构成投资建议”。

## 任务分解

### P3-0：契约冻结与技术选型 ADR

- **状态**：待开始。
- **目标**：固定 HTTP 边界、目录结构、启动方式、JSON 契约和错误映射。
- **产物**：P3 ADR、API 契约样例、安全边界清单、受影响文件清单。
- **验收条件**：
  - 明确采用标准库 HTTP 服务或经用户批准的 Web 框架。
  - 明确静态资源目录、模板目录和数据库路径只由服务端配置。
  - 明确 Decimal、Enum、日期、dataclass 和三态结果的 JSON 表示。
  - 明确临时模板运行与已保存模板运行的语义。
  - 本任务不修改业务行为。
- **依赖**：P2-9。

### P3-1：规则目录序列化与前端发现契约

- **状态**：待开始。
- **目标**：将注册表中的规则元数据稳定地暴露给前端。
- **产物**：规则目录应用服务或序列化器、`GET /api/rules` 契约测试。
- **验收条件**：
  - 输出来自 `RuleRegistry.definitions()`，不维护第二份规则清单。
  - Decimal、Enum 和边界值具有稳定 JSON 表示。
  - 注册一个测试规则后，目录自动包含它，不修改 Web 代码。
  - 重复 ID、空 ID 等仍由 P2 注册表拒绝。
- **依赖**：P3-0。

### P3-2：本地 HTTP 应用骨架与安全启动命令

- **状态**：待开始。
- **目标**：建立无 Provider 依赖的本地 HTTP 接口层。
- **产物**：Web 应用工厂、静态资源服务、`stock-manager web` 启动命令、健康检查。
- **验收条件**：
  - 默认只监听 `127.0.0.1`，端口配置化。
  - 启动前验证 SQLite 存在；不得为筛选偷偷创建空数据库。
  - 请求体大小受限，未知路由返回结构化 404。
  - 静态资源只从固定白名单提供，不接受任意文件路径。
  - Web 模块不导入 Baostock Provider 或 `DataSyncService`。
- **依赖**：P3-0、P3-1。

### P3-3：模板查询、校验与保存 API

- **状态**：待开始。
- **目标**：把 P2 模板生命周期以薄 API 暴露给页面。
- **产物**：模板列表、详情、校验、创建、更新和删除端点。
- **验收条件**：
  - 所有写入均调用 `TemplateService`，保存前完整编译。
  - 系统模板只读；路径穿越和非法 ID 继续被拒绝。
  - 更新和删除必须携带 `expected_revision`。
  - revision 冲突返回 409，禁止最后写入者静默覆盖。
  - API 测试使用临时目录，不修改真实用户模板。
- **依赖**：P3-2。

### P3-4：离线筛选 API

- **状态**：待开始。
- **目标**：支持页面以临时模板运行参数化筛选。
- **产物**：`POST /api/screen`、输入模型、输出序列化和错误映射。
- **验收条件**：
  - 请求模板始终经过 P2 解析与编译。
  - 只调用 `ParameterizedScreeningService` 和本地 Repository。
  - 请求复权、模板复权和数据集复权三方一致。
  - 无数据、非交易日、股票不存在和样本不足语义可区分。
  - 单元/集成测试断网通过，并证明 Provider 未被调用。
- **依赖**：P3-2、P3-3。

### P3-5：动态参数化策略编辑器

- **状态**：待开始。
- **目标**：根据规则目录自动生成规则卡片和参数控件。
- **产物**：HTML、CSS、JavaScript 策略编辑器。
- **验收条件**：
  - 页面源码中没有八条内置规则 ID 的硬编码列表。
  - `integer`、`decimal`、`boolean`、`text` 均有正确控件和取值转换。
  - 显示参数标签、说明、默认值和最小/最大边界。
  - 可开关规则、选择分组并编辑组内/顶层 `all` 或 `any`。
  - 至少一条规则启用、唯一组合归属等错误在提交前提示；后端仍二次校验。
- **依赖**：P3-1、P3-3。

### P3-6：模板工作流与状态管理

- **状态**：待开始。
- **目标**：在页面完成加载、编辑、验证、保存、另存为和删除。
- **产物**：模板选择器、脏状态、revision 状态和冲突处理。
- **验收条件**：
  - 系统模板编辑后只能另存为用户模板。
  - 临时筛选不会自动保存。
  - 用户模板更新后 revision 在界面同步递增。
  - 切换有未保存改动的模板时给出确认。
  - 删除仅对用户模板开放并要求明确确认。
- **依赖**：P3-3、P3-5。

### P3-7：筛选结果可视化

- **状态**：待开始。
- **目标**：让总体筛选结果和规则失败原因可读、可追踪。
- **产物**：统计摘要、结果表、状态筛选、逐规则详情面板。
- **验收条件**：
  - 明确显示总数、通过数、失败数和所用模板 revision。
  - 每只股票显示代码、名称、目标日和总体状态。
  - 逐规则显示状态、`actual_value`、`threshold` 和 `reason`。
  - `SKIPPED` 与 `FAILED` 视觉和语义不同。
  - 空结果、加载中、服务错误和数据缺失均有明确界面状态。
  - 页面包含研究用途免责声明。
- **依赖**：P3-4、P3-5。

### P3-8：新规则端到端扩展性验收

- **状态**：待开始。
- **目标**：证明普通后端规则可沿元数据链路自动出现在页面并参与筛选。
- **产物**：仅用于测试的示例规则、扩展契约测试、开发者检查表。
- **验收条件**：
  - 新增测试规则只需定义参数、数据需求、求值并注册。
  - `/api/rules` 自动出现新规则及全部参数。
  - 前端通用渲染器自动生成控件，不修改 HTML/JS 规则清单。
  - 模板可启用该规则、编译并返回逐规则结果。
  - 若新规则需要现有 `RuleContext` 不支持的数据类型，测试明确要求先扩展领域与 Repository，禁止规则自行查库或联网。
- **依赖**：P3-1、P3-4、P3-5、P3-7。

### P3-9：离线端到端、浏览器验收、文档与同步

- **状态**：待开始。
- **目标**：完成从页面编辑到本地筛选结果展示的完整验收。
- **产物**：HTTP 集成测试、浏览器交互验收记录、使用文档、API 文档、规则扩展文档和 Obsidian 同步副本。
- **验收条件**：
  - 全量单元测试断网通过且不产生仓库缓存或构建物。
  - 浏览器完成默认模板加载、参数修改、临时筛选、另存为、更新冲突和结果详情检查。
  - 验证窄屏和常见桌面宽度，无阻断性布局问题。
  - 文档与真实代码、端点、字段和测试结果一致。
  - Qwen 若参与，仅能在代码验收后按完整任务包起草注释和 Markdown；业务代码、测试、配置和构建脚本仍由架构实现代理负责。
  - 所有技术文档包含规定 frontmatter，并同步到 Obsidian `项目文档`。
- **依赖**：P3-0 至 P3-8。

## 新增规则的标准路径

普通规则扩展完成后，链路应为：

```text
新增纯规则与强类型参数
  -> 声明 RuleDefinition
  -> 声明 RuleDataRequirement
  -> build_default_registry 显式注册
  -> /api/rules 自动输出
  -> 前端自动生成参数控件
  -> 模板编译
  -> ParameterizedScreeningService 执行
  -> 结果页展示 RuleExecutionResult
```

需要修改通用框架的情况仅限：新增参数类型、新组合运算符，或规则需要 `RuleContext` 尚不支持的新数据域。这些属于架构升级，必须先写 ADR、扩展本地 Repository 和数据同步边界，不能在规则内部绕过分层。

## 完成定义

P3 只有同时满足以下条件才可标记完成：

1. 页面不硬编码内置规则清单，新注册普通规则可自动发现和渲染。
2. 所有筛选请求只读本地 SQLite，断网可运行，Web 路径不持有 Provider。
3. 模板解析、参数校验、组合校验和 revision 冲突仍由后端权威处理。
4. 系统模板只读，用户模板 CRUD、临时筛选和错误状态均有测试。
5. 结果页准确区分 `PASSED`、`FAILED`、`SKIPPED` 并展示结构化原因。
6. API、规则扩展、静态资源安全和关键浏览器交互均通过验收。
7. 所有新增或修改函数具有完整类型标注，无吞异常和本机绝对路径硬编码。
8. 文档经代码事实核对并同步至 Obsidian。
9. Git 提交聚焦、符合 Conventional Commits，未纳入缓存、日志、IDE 文件、数据库或构建物。

## 建议执行顺序

```text
P3-0
  -> P3-1
  -> P3-2
  -> P3-3 + P3-4
  -> P3-5
  -> P3-6 + P3-7
  -> P3-8
  -> P3-9
```

P3-0 是契约门；P3-8 是扩展性门；P3-9 是最终验收门。任何阶段都不得为了页面方便绕过 P2 的编译器、服务层或本地优先边界。
