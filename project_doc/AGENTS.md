# StockManager 项目开发规定

## 1. 项目定位与核心约束

### 1.1 项目性质

本项目为 **A 股研究型筛选平台**。

- **核心目标**：构建可测试、可维护的股票筛选内核。
- **严格禁止**：自动交易功能。
- **免责声明**：所有筛选结果仅供研究参考，**不构成任何投资建议**。

### 1.2 数据源策略

- **当前数据源**：Baostock。
- **架构要求**：Provider 层必须保持可替换性（接口抽象），严禁在业务代码中硬编码 Baostock 特定逻辑，严禁擅自切换数据源。
- **复权策略**：
  - **禁止**擅自假定默认复权方式。
  - **必须**在每个数据集和规则中明确记录复权方式（如：不复权、前复权、后复权）。
  - 具体的复权策略由架构决策另行确定，AI 不得擅自决定。

### 1.3 代码状态

- **旧代码**：保留为 `legacy` 参考，不得直接依赖。
- **新内核**：优先建设可测试的筛选内核，逐步替换旧逻辑。

### 1.4 默认项目知识源

项目规范路径如下：

- 项目根目录：`/Users/douzihao/StockManager`。

`project_doc` 内部按「开发手册」与「使用手册」组织，目录名均为英文：

## 2. 架构分层规范

系统必须遵循以下分层结构，确保网络、存储和业务规则分离：

1. **Domain（领域层）**：定义核心实体，如 Stock、Signal、RuleResult。
2. **Rules（规则层）**：
   - 筛选规则必须是无副作用的纯函数。
   - 输入为结构化数据。
   - 输出为结构化筛选结果。
3. **Providers（数据提供层）**：
   - 封装 Baostock 等数据源。
   - 负责数据获取、清洗和格式标准化。
   - 必须处理交易日历、时区和复权标记。
4. **Services（服务层）**：编排 Rules 和 Providers，处理业务流程。
5. **Storage（存储层）**：提供数据持久化接口；禁止在 Rules 或 Domain 层直接操作数据库。
6. **API（接口层）**：对外暴露服务，负责请求解析和响应格式化，不包含筛选业务逻辑。

## 3. 数据规则与时间处理

### 3.1 交易日历

- 所有时间处理必须基于 `Asia/Shanghai`。
- **禁止**使用“自然日前一天”冒充“上一交易日”。
- **必须**根据 A 股交易日历确认有效交易日。
- 若当前日期不是交易日，必须回溯到最近的有效交易日。

### 3.2 数据元数据

每个数据集必须记录：

- 数据来源。
- 数据获取或生成时间。
- 复权方式，如 `unadjusted`、`qfq`、`hfq`。

## 4. 代码规范

### 4.1 通用约束

- 所有新增或修改的函数必须包含完整类型标注。
- **禁止**吞掉异常，包括 `try...except: pass` 或捕获未知异常后直接返回普通筛选失败。
- **禁止**用日志代替异常处理；必须捕获具体异常并向上抛出或转换为明确的业务异常。
- **禁止**硬编码本机绝对路径；路径必须通过配置或受控的相对路径提供。

### 4.2 筛选结果结构

筛选规则必须返回结构化对象，至少包含：

- `passed: bool`：是否通过。
- `actual_value`：实际计算值。
- `threshold`：使用的阈值或条件。
- `reason: str`：通过说明或未通过原因。

### 4.3 Git 忽略规则

以下文件或目录不得进入 Git：

- IDE 配置，如 `.vscode`、`.idea`。
- 日志文件，如 `*.log`。
- 缓存文件，如 `__pycache__`、`.pytest_cache`。
- 构建产物，如 `dist`、`build`。
- Excel 输出，如 `*.xlsx`、`*.xls`。
- 可执行文件，如 `*.exe`、`*.bin`。

## 5. 测试规范

### 5.1 测试原则

- 单元测试**禁止联网**，必须使用固定、可复现的 fixtures。
- Bug 修复必须遵循：先编写可复现 Bug 的失败测试，再修复代码，最后确认测试通过。
- 不机械要求 100% 覆盖率，但关键规则和关键分支必须有测试。

### 5.2 必测场景

- 边界值，包括最大值、最小值和零值。
- 缺失值，包括 `None`、`NaN`。
- 停牌、ST、涨停和跌停。
- 空数据集合。
- 数据顺序异常。
- 关键业务规则的所有分支。

## 6. Git 工作流

- `main` 分支必须保持可运行状态。
- 使用短期功能分支进行开发，不假设必须存在 `dev` 分支。
- 提交信息遵循 Conventional Commits，例如 `feat:`、`fix:`、`docs:`、`test:`。
- 每次提交必须聚焦一个明确目的，并清楚描述变更内容。

### 6.1 版本控制原则

项目版本号采用语义化版本格式 `MAJOR.MINOR.PATCH`，并遵循以下递增规则：

- **主版本（MAJOR）**：发生不兼容的破坏性变更时递增。
- **次版本（MINOR）**：**加入新规则/新功能**（向后兼容）时递增，即 `+0.1.0`。
- **修订版本（PATCH）**：**加入新 UI 内容**（向后兼容）时递增，即 `+0.0.1`。

修改版本号时必须同步更新以下位置并保持一致：

- `pyproject.toml` 中的 `version` 字段。
- `src/stock_manager/__init__.py` 中的 `__version__`。
- `tests/test_package_structure.py` 中的版本断言。

## 7. 需求澄清与协作流程

### 7.1 用户提需求，Agent 追问细化

新功能、架构调整或尚未明确的产品想法，默认采用“用户提出需求 → Agent 追问 → 整理需求 → 确认范围 → 执行与验收”的协作方式。

- 先阅读 `project_doc/README.md` 及相关计划、ADR 和使用手册，必要时核对代码，复述对需求的理解；已有明确答案不重复询问。
- 主动提出大量、具体、系统的问题，不设每轮问题数量上限；以需求覆盖充分、项目计划（plan）尽量精确为目标，不为缩短对话而省略必要追问。
- 问题按主题分组并编号，可先给出完整问题清单，再分批讨论；根据回答继续深挖细节、矛盾与遗漏，直至影响实现和验收的歧义得到澄清。已有明确答案不重复询问，问题应服务于计划精度。

- 明确区分“用户已确认”“Agent 建议”“待决定”，不得把建议或猜测写成用户需求。
- 用户只要求讨论、方案或架构时，先完成需求与设计，不进入代码实现。

### 7.2 形成可执行的需求约定

需求澄清的主要产物是尽量精确、可执行、可验收的项目计划（plan）。进入实现前，将讨论结果整理为详细计划，按任务适用范围明确：

1. 目标与场景：目标用户、要解决的问题、典型使用流程和预期结果。
2. 范围与优先级：本次必须完成、可延期及明确不做的内容，避免隐含扩展。
3. 输入输出与接口：数据结构、字段、类型、参数、默认值、单位、取值范围及兼容要求。
4. 业务与数据口径：计算公式、时间窗口、交易日历、复权、数据来源、缺失值及排序规则；未决定的口径明确标注。
5. 交互与异常：正常流程、边界条件、空数据、失败状态、错误提示、重试与恢复行为。
6. 架构与实施：模块边界、任务拆分、依赖顺序、阶段交付物，以及适用的性能、并发、存储和迁移约束。

8. 决策与待决项：已确认结论、采用方案及取舍、尚未确认的假设、待用户决定的问题；不适用的项目注明原因。

计划应让后续实现者无需猜测关键需求即可执行。每轮问答后持续更新计划与待决清单；涉及用户意图、业务口径或验收标准的待决项应在相关实现开始前确认，不得用未经确认的假设填补。

- 对意图明确、范围有限的修错字、文档更新和小修改，直接执行；只有影响目标、正确性或重要边界的不确定项才需要追问。
- 常规实现细节由当前负责的 Agent 在既定范围内处理。若新增需求改变公共接口、数据口径或验收目标，说明变化和影响后再确认。

## 11. 外部数据访问与本地优先规定

本章节定义 StockManager 项目中数据获取、存储及访问的强制性架构约束。所有代码实现、测试及验收必须严格遵守以下规则，任何违反本规定的代码不得通过验收。

### 1. 数据访问边界
- **单一入口原则**：Baostock 等外部数据源**仅允许**由 `DataSyncService` 调用。
- **只读本地存储**：筛选引擎（Screening）、规则执行（Rules）、API 接口及 CLI 查询命令**严禁**直接调用外部数据源。所有查询必须且只能读取本地 SQLite 数据库。
- **禁止反向依赖**：筛选路径（ScreeningService -> Rules）不得持有或调用 Provider 实例。

### 2. 防重复与幂等性
- **成功即锁定**：同一数据集（Dataset）在特定交易日（Trading Day）成功同步后，系统必须标记该状态。
- **拒绝重复拉取**：若检测到该交易日数据已存在且同步成功，任何新的同步请求必须：
  1. 发出用户可见的警告（Warning），提示“数据已存在，跳过拉取”。
  2. 直接返回本地已有数据，**不得**发起网络请求。
- **并发保护**：同步操作必须使用持久化锁（文件锁或数据库锁）和进程锁，防止用户连点或并发进程导致的重复调用。

### 3. 同步策略与时间基准
- **时间基准**：自动同步以 `Asia/Shanghai` 时区为准。
- **最新已完成交易日**：同步目标为“最新已完成交易日”。该日期必须根据交易日历和数据可用截止时间（Cutoff Time，配置化）计算，**不得**简单使用自然日当天。
- **自动补齐机制**：
  - 程序进入新的最新已完成交易日后，**首次启动**时自动触发同步。
  - 若程序在数据更新窗口期未运行，则**下次启动**时自动补齐缺失数据。
  - **不承诺**后台常驻运行或系统级调度，仅依赖应用启动时的检查。
- **完整性判定**：交易日仅当当日去重 bar 股票数 ≥ 股票池规模的 95% 时才视为同步完整；对无同步记录的历史交易日若覆盖不足，必须标记为 `incomplete` 并在界面以琥珀色提示，不得视为成功或完整。

### 4. 失败处理与重试
- **失败不记成功**：同步失败必须明确记录为 `FAILED` 状态，严禁标记为成功或部分成功。
- **显式重试**：重试必须由用户显式触发（如 CLI `sync --retry`），禁止无限自动重试。
- **冷却与限流**：重试机制必须包含冷却时间（Cooldown）和速率限制，防止对上游服务造成压力。
- **失败日回补刷新**：自动回补遇到标记为 `FAILED` 的交易日必须重新拉取刷新，不得跳过；成功交易日仍受防重复拉取约束。

### 5. 速率控制
- **串行执行**：Provider 请求必须按受控速率串行执行。
- **禁止无限制并发**：严禁使用无上限的并发池或异步并发批量拉取数据，必须遵守 Baostock 等数据源的速率限制。
- **上游挂起防护**：Provider 请求必须设置 socket 超时，防止上游无响应导致同步挂起。

### 6. 验收红线
- 任何绕过“本地优先”原则的代码（如筛选时直接查网）不得验收。
- 任何绕过“防重复”机制的代码（如允许同一交易日多次拉取）不得验收。
